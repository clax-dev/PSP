NIVEL BAJO · ReentrantReadWriteLock

Un objeto, dos cerrojos: readLock() y writeLock()

¿Quién puede entrar?

Dentro hay… \ llega…LectorEscritor
Nadie✅ entra✅ entra
1 o más lectores✅ entra❌ espera
Un escritor❌ espera❌ espera
readLock()
COMPARTIDO: muchos a la vez.
writeLock()
EXCLUSIVO: uno y nadie más.
ReadWriteLock = interfaz (solo define los 2 métodos)
ReentrantReadWriteLock = la clase que la implementa
Los dos cerrojos son Lock: lock(), unlock(), tryLock()…

Cómo se usa

ReadWriteLock rw = new ReentrantReadWriteLock();
Lock lectura   = rw.readLock();
Lock escritura = rw.writeLock();

// LEER (muchos hilos a la vez)
lectura.lock();
try {
    return precio;
} finally {
    lectura.unlock();   // SIEMPRE
}

// ESCRIBIR (uno solo, sin lectores)
escritura.lock();
try {
    precio = nuevo;
} finally {
    escritura.unlock(); // SIEMPRE
}

El escritor espera… y los nuevos lectores no se cuelan

Starvation: si los lectores pudieran colarse siempre…

Fairness (justicia)

ConstructorComportamiento
new ReentrantReadWriteLock()No justo (por defecto): más rápido, sin orden garantizado
new ReentrantReadWriteLock(true)Justo: por orden de llegada → sin starvation, pero más lento

Subir y bajar

tengo readLock → pido writeLock❌ me bloqueo para siempre (me espero a mí)
tengo writeLock → pido readLock✅ se puede (downgrade)

NIVEL BAJO · StampedLock

tryOptimisticRead() → copiar → validate(stamp)

Línea de tiempo: el escritor NO espera al lector optimista

Demo L04 (salida real): de 200 lecturas optimistas, 40 fallaron validate; 32 de ellas eran copias a medias. Datos incoherentes usados: 0.
Limitaciones: hay que validar siempre · no usar los datos antes de validar · solo para leer · con muchas escrituras falla mucho · StampedLock no es reentrante.
tryConvertToWriteLock(stamp): intenta pasar a escritura sin soltar. Devuelve el nuevo stamp o 0 si no puede.

CONCLUSIONES · CASOS DE USO

¿Cuál elijo?

Cuándo NO compensa
  • Secciones críticas cortísimas (leer un int)
  • Casi tantas escrituras como lecturas
  • Pocos hilos o poca competencia
  • Ya existe ConcurrentHashMap, CopyOnWriteArrayList…
  • Datos inmutables: no hay nada que proteger
// Regla de oro: liberar SIEMPRE
lock.lock();          // fuera del try
try {
    ...
} finally {
    lock.unlock();    // aunque haya excepción
}
// Si no: el lock queda cogido para siempre
// y el programa se congela SIN ningún error.
